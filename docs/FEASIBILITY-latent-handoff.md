# Осуществимость: перенос сырого латента между сценами

Оценка приёма из `.superpowers/h3-continuation-recon.md` (H3 Motion Context / H3 Continuum)
против *нашего* кода. Сцена N+1 получает не PNG-кейфрейм, а срез уже расшумлённого видео-латента
хвоста сцены N — без декода и без обратного прохода через VAE. Ничего не реализовано; всё ниже
получено чтением кода и арифметикой по формам из него. GPU не трогался, тесты не гонялись.

**Вердикт.**

| | Вердикт | Объём | Стоимость прогона |
|---|---|---|---|
| Видео-латент, перенос хвоста | **Делаемо**, своей правкой, без monkeypatch | ~27–35 ч | m=0: **0%**; m=1: +21% (448×288) / +28% (896×512) диффузии |
| Аудио-латент | Не делаем (стройка с нуля, см. §2) | — | — |
| Лечение идентичности персонажей | **Не решает.** Возможно, делает хуже (§4.5) | — | — |

Главное, что удешевляет задачу против ожиданий: **хвост латента уже лежит в нужном
пространстве и в нужной раскладке строк** — сохранение сводится к срезу массива, загрузка к
`mx.load`, никаких преобразований (§1.2). И **при переносе двух латентных кадров (0.208 с)
длина упакованной последовательности не растёт вовсе** — картиночный кейфрейм стоит ровно
столько же строк, сколько два латентных кадра (§1.5).

## 1. Точная карта изменений

### 1.1 `upstream/minimax_h3_mlx/packing.py` — обобщение позиций кондиционирования

Сейчас `build_packed_sequence` (packing.py:252–345) принимает `keyframe_anchors: tuple[str, ...]`
(packing.py:259) и знает ровно два литерала (packing.py:293–301):

```python
for index, anchor in enumerate(keyframe_anchors):
    if anchor == "first":
        anchor_time = float(num_text)
    elif anchor == "last":
        anchor_time = (
            float(num_text) + _temporal_position_span(num_latent_frames) - _ROPE_FRAME_RESCALE
        )
    else:
        raise ValueError(f"A keyframe anchor must be 'first' or 'last', got {anchor!r}.")
    lo = condition_start + index * rows_per_frame
    hi = condition_start + (index + 1) * rows_per_frame
    position_ids[lo:hi, 0] = anchor_time
    position_ids[lo:hi, 1:] = frame_grid
```

Обе ветки — частные случаи одной формулы. `_temporal_position_span(F)` (packing.py:240–249) для
`F = 5n+2` даёт `(17n+5) * 5/3`, то есть `num_frames * FRAME_RESCALE`; минус один
`_ROPE_FRAME_RESCALE` — это `FRAME_RESCALE * (num_frames − 1)`. Значит:

```
anchor_time = num_text + _ROPE_FRAME_RESCALE * pixel_index
              pixel_index = 0             для "first"
              pixel_index = num_frames-1  для "last"
```

Ровно то, что monkeypatch Motion-Context'а прописывает в чужой `PackedLayout` (recon §2). У нас
это свой файл — обобщение выглядит так:

```python
keyframe_anchors: tuple[str | int, ...] = ()
...
    if anchor == "first":
        anchor_time = float(num_text)                       # НЕ трогать
    elif anchor == "last":
        anchor_time = (                                     # НЕ трогать
            float(num_text) + _temporal_position_span(num_latent_frames) - _ROPE_FRAME_RESCALE
        )
    elif isinstance(anchor, (int, np.integer)):
        anchor_time = float(num_text) + _ROPE_FRAME_RESCALE * float(int(anchor))
    else:
        raise ValueError(...)
```

**Две строковые ветки остаются побайтово прежними намеренно.** Докстринг
`_temporal_position_span` (packing.py:240–249) прямо предупреждает: numpy суммирует попарно, и
начиная с 16 латентных кадров это отличается от последовательной суммы в последнем ulp. Значит
`FRAME_RESCALE * (num_frames − 1)`, посчитанное напрямую, *может* не совпасть с текущей веткой
`"last"` бит-в-бит. Переписывать обе ветки через новую формулу — значит менять уже
оттестированный i2v/flf на величину, которую никто не мерил. Тест на новую ветку должен
утверждать точное равенство с `"first"` при `pixel_index=0` и **измерять**, а не постулировать,
расхождение с `"last"` при `pixel_index=num_frames−1`.

Больше в `packing.py` менять нечего: `num_condition_rows = len(keyframe_anchors) * rows_per_frame`
(packing.py:273) уже считает L блоков, `video_idx` (packing.py:325–327) уже кладёт строки
кондиционирования перед целевыми, `build_row_timesteps` (packing.py:348–377) уже пришпиливает
первые `n_cond_v` видео-строк к отдельному таймстепу.

`num_condition_audio_rows=0` (packing.py:344) остаётся нулём — см. §2.

### 1.2 `pipeline.py` — где латент ещё сырой, и как принять его обратно

**Где он сырой.** Единственная точка — `upstream/minimax_h3_mlx/pipeline.py:346`:

```python
video = self._decode_video(video_rows[n_cond_v:], num_latent_frames, latent_height, latent_width)
```

`video_rows[n_cond_v:]` — это финальный латент в *patchified* виде: `(F * rows_per_frame, 96)`,
float32, уже нормализованный `(x − latents_mean) / latents_std`. Денормализация происходит только
внутри декода (upstream pipeline.py:366; форк — `h3_48gb/pipeline.py:420`), `unpatchify` — там же
(upstream :361, форк :414).

В форке эти же строки приходят в `LazyMiniMaxH3Pipeline._decode_video`
(`h3_48gb/pipeline.py:379`), где на :407 стоит `mx.eval(rows)` перед выгрузкой DiT. **Шов для
сохранения — между `h3_48gb/pipeline.py:407` и :414**: строки материализованы (значит запись не
затянет в себя весь forward — та самая ловушка `written_at`, `checkpoint.py:646–654`), DiT ещё не
выгружен, VAE ещё не тронут.

**Почему это дёшево.** Хвост — просто срез по строкам. Раскладка `patchify_video_latents`
(packing.py:169–181) — frame-major (`transpose(0,2,4,6,1,3,5,7)`), поэтому

```python
tail = rows[(num_latent_frames - L) * rows_per_frame:]      # (L * rows_per_frame, 96)
```

это ровно последние `L` латентных кадров, в том же порядке, в каком `_encode_keyframes`
(upstream pipeline.py:190–207) конкатенирует по одному блоку на картинку. Пространство совпадает:
`_encode_keyframes` нормализует на :205 тем же `(latent − mean) / std`. **Ни одного преобразования
между сохранением и приёмом нет.**

**Приём.** `_encode_keyframes` (upstream :165–207) умеет строить строки только из картинок через
`video_vae._encode_clip`, и его переопределение в форке (`h3_48gb/pipeline.py:322–360`)
существует только ради порядка seed'а и выгрузки VAE. Латентный путь идёт мимо него целиком.
Правка в `MiniMaxH3Pipeline.__call__` (upstream :267–291):

```python
        # 3. Keyframe conditioning rows, encoded before any request noise is drawn.
        condition_rows = None
        if condition_latent_rows is not None:          # НОВОЕ: приходит уже готовым
            condition_rows = condition_latent_rows
        elif images:
            condition_rows = self._encode_keyframes(images, height, width)
```

плюс новый параметр `condition_latent_rows: mx.array | None = None` в сигнатуре (upstream :211–224).
Три обязательных проверки в новой ветке, все — «падать громко»:

* `condition_latent_rows.shape == (len(keyframe_anchors) * rows_per_frame, dit.config.video_patch_dim)`;
  несовпадение = чужая геометрия (recon §5: «resolution can't change mid-chain»);
* `dtype == float32` (checkpoint пишет то же самое, `checkpoint.py:618–640`);
* `images` и `condition_latent_rows` одновременно — отказ, если только явно не запрошена схема
  «латент + картинка» (§3), потому что при обоих `_encode_keyframes` тоже вернёт строки и
  конкатенация в `video_rows` (upstream :289–290) разъедется с `num_condition_rows`.

**Открытый вопрос — шум.** Строки кондиционирования не чистые: upstream :275–280 зашумляет их до
`t = 0.999` (`KEYFRAME_NOISE_AUG`, packing.py:64), а `_row_timestep_plan` (upstream :125–145)
держит их на `max(t, 0.999)` все шаги. Для картиночного кейфрейма это документировано; для сырого
латентного хвоста recon §6(b) и «What wasn't resolved» честно говорят: ни один из разобранных
проектов этого не решает. **Рекомендация: по умолчанию зашумлять так же** — модель на этом
таймстепе строки и ждёт, а подача чистого латента в слот, размеченный как 0.999, — режим, на
котором никто не обучался. Флаг `--latent-noise-aug/--latent-clean` для A/B; проверка стоит два
прогона по ~10 мин на 448×288.

Дополнительно: float16-округление (upstream :204) к латентному хвосту **не применять** — оно
воспроизводит округление референса внутри VAE-энкода посторной выборки, а тут никакого энкода нет.

### 1.3 `checkpoint.py` / CLI — сохранение хвоста на диск

**Не через чекпоинт.** Финальный чекпоинт действительно содержит готовый латент (`video_gen`,
`checkpoint.py:636`), но при успехе он удаляется (`checkpoint.py:868–870`, `store.discard()`), а
несёт с собой ещё и `prompt_embeds` — мегабайты, которые следующей сцене не нужны. Отдельный
файл дешевле и честнее.

**Формат.** `mx.save_safetensors` (та же функция, что у чекпоинта, `checkpoint.py:379`), атомарно
через temp+`os.replace` (`checkpoint.py:365–396` — шаблон уже есть, как и в `run_generate` для
`-raw.npz`, `cli.py:949–967`):

```
<stem>-latent-tail.safetensors
  arrays:   video_tail  (L * rows_per_frame, 96) float32
  metadata: {"format": 1, "canvas": [W, H], "latent_frames": L,
             "rows_per_frame": R, "num_frames": R_frames, "patch_size": [1,2,2],
             "pinned_pixel_indices": [0, 1, 5, 9, 13, 17, 18],
             "source_identity_digest": "<identity_digest прогона-источника>"}
```

`pinned_pixel_indices` — именно то, что уйдёт в `keyframe_anchors` следующей сцены (§1.4);
писать их, а не вычислять заново на приёме, чтобы формула жила в одном месте.

**Сетка, на которой можно резать.** Временная сетка латентных кадров в пиксельных индексах —
`0, 1, 5, 9, 13, 17, 18, 22, …` (проверено прогоном арифметики `_temporal_position_grid`,
packing.py:228–237). Кадр с индексом `5m` стоит в пикселе `17m`, и дальше шаблон
`(1,4,4,4,4)` повторяется — то есть **хвост из `L = 5m+2` латентных кадров ложится на
собственную стартовую сетку следующей сцены один в один**, покрывая `17m+5` пиксельных кадров:

| m | L (латентных кадров) | окно | секунд @24fps | комментарий |
|---|---|---|---|---|
| 0 | 2 | 5 кадров | 0.208 | минимальный вариант, бесплатный по строкам (§1.5) |
| 1 | 7 | 22 кадра | 0.917 | дефолт Motion-Context (recon §1: «22 видеокадра ≈ 1 с») |
| 2 | 12 | 39 кадров | 1.625 | |
| 3 | 17 | 56 кадров | 2.333 | |

Ряд `5, 22, 39, 56` — ровно `17m+5`, тот же список, что у Motion-Context. Совпадение не случайно:
это и есть родная сетка VAE (`FRAMES_PER_CHUNK`/`LATENTS_PER_CHUNK`, packing.py:46–47).

**Размер на сцену.** Строка = `latents_dim * prod(patch_size)` = `24 * 1 * 2 * 2` = **96 float32**
(`DiTConfig.video_patch_dim`, `config.py:59–61`). Строк на латентный кадр = `(H/16/2) * (W/16/2)`,
где 16 — `spatial_compression_ratio` (`space_down = [2,2,2,2,1,1]`, video_vae.py:54–59).

| канва | строк/латентный кадр | m=0 (L=2) | m=1 (L=7) | m=2 (L=12) | весь финальный латент (209 кадров) |
|---|---|---|---|---|---|
| 448×288 | 126 | **94.5 кБ** | **331 кБ** | 567 кБ | 3.00 МБ |
| 896×512 | 448 | **336 кБ** | **1.18 МБ** | 2.02 МБ | 10.67 МБ |

На 38-сценный проект при 896×512 и m=1 — 44.7 МБ, против 80 МБ, которые проект весит целиком
после уборки. Значит `latents/` обязан попасть в `_cleanup_project_artifacts`
(`assemble.py:802–888`) рядом с `keyframes/` (:877–885).

**CLI.** В `RunSpec` (`cli.py:278–345`) два поля и два флага в `_add_run_flags`
(`cli.py:440–505`, рядом с `--image`/`--end-image` на :464–467):

* `--save-latent-tail N` — сохранить хвост из N латентных кадров (`N ∈ {2,7,12,17}`, проверка в
  `__post_init__`, `cli.py:347`); путь производный от `output_stem()` (`cli.py:430`);
* `--latent <path>` — принять хвост как условие; несовместим с `--image` по умолчанию
  (новый код в `ERROR_CODES`, `cli.py:148`, по образцу `end_image_without_image` на :157).

`load_keyframes` (`cli.py:780–832`) получает сестринскую `load_latent_tail(spec)`, возвращающую
`(condition_latent_rows, keyframe_anchors)` — второй элемент читается прямо из
`pinned_pixel_indices` метаданных. Вызов в `run_generate` (`cli.py:915–930`) дополняется двумя
kwargs; `pop_checkpoint_kwargs`/`pop_preview_kwargs` не затрагиваются, потому что новые аргументы
принадлежат апстримовой сигнатуре, а её и биндит `LazyMiniMaxH3Pipeline.__call__`
(`h3_48gb/pipeline.py:601`).

Запись — в `_decode_video` по шву :407 (§1.2), а не в `run_generate`: там латента уже нет, есть
только uint8-кадры.

### 1.4 `assemble.py` / `worker.py` — передача файла вместо PNG

`worker.py` **не меняется вовсе**: `job_command` (`worker.py:73–83`) прокидывает `job.args`
дословно, а `_validate_args_shape_for_kind` (`queue.py:602–628`) для `kind="generate"` проверяет
только, что `args[0]` не `song`/`assemble`. Новый флаг проезжает сам собой.

Меняется `assemble.py`:

1. **`_scene_generate_args` (`assemble.py:962–1016`)** — вместо `--image <keyframe>` (:1012–1013)
   для сцепленной сцены подставляет `--latent <path>` и **не** приклеивает
   `SCENE_I2V_INSTRUCTION` (:129–132, применяется на :1005): фраза «`<Picture 1>` … is fully
   referenced» обещает картинку, которой в запросе больше нет. Плюс `--save-latent-tail N` —
   каждой сцене, кроме последней.
2. **`_submit_next_scene` (`assemble.py:1070–1153`)** — блок `idx > 0` (:1115–1121) вместо
   `_extract_keyframe(prev_clip, …)` берёт `prev["latent_tail_path"]`. `_extract_keyframe`
   (`assemble.py:1023–1063`) для сцепленных сцен из цепочки уходит целиком — вместе с ffmpeg-
   извлечением, откатом на 24 кадра по `framecheck` и каталогом `keyframes/`. Остаётся для
   `fresh_start`-сцен, если те всё же должны стартовать с картинки.
3. **Новое поле сцены `latent_tail_path`** — по образцу `keyframe_path`
   (`project.py:574–608`); схемы у `project.json` нет (валидации jsonschema в `project.py` не
   обнаружено), но `set_scene_status` придётся расширить третьим необязательным полем и
   очищать его в `invalidate_scene_chain` вместе с двумя существующими.
4. **`_drop_first_frame` → `_drop_head_frames(n)`** (`assemble.py:248–272`). Сейчас фильтр
   `trim=start_frame=1` снимает ровно один дублирующий кадр; при переносе латента голова
   следующего клипа воспроизводит `17m+5` кадров хвоста предыдущего, и снимать надо именно
   столько: `trim=start_frame=<17m+5>`. Длина известна заранее и детерминированно — как и у
   обоих ComfyUI-проектов (recon §4), никакого пиксельного детектирования шва.
   `_chaining_scene_indices` (:237–246) и `_build_video_clip_paths` (:275–292) остаются, но
   должны знать `m` сцены — берётся из метаданных её латентного входа.
5. **`_cleanup_project_artifacts` (:802–888)** — добавить `latents/` к сносимому.

`_handle_project_scene_result` (`worker.py:554–640`) не меняется: он читает только
`clip_path = f"{job.output_stem}.mp4"` (:626), а путь хвоста производный от того же stem и
вычисляется в `assemble`.

### 1.5 Что это стоит по строкам и по времени

Модель стоимости — `docs/RESULTS.md` («Predicting wall clock»):
`seconds ≈ 5.699e-3 * rows + 2.671e-7 * rows²` на один forward, попадание в 3% на пяти точках.
Строки текста: ~124 токена промпта сцены + блок зрения. **Токенов зрения ровно
`(H/32) * (W/32)`** (Qwen3-VL: patch 16, merge 2; `preprocessor_config.json`, обработка —
`text_encoder.py:192–207`) — то есть **ровно столько же, сколько строк даёт один латентный
кадр**. Это не совпадение: обе величины — `(H/32)*(W/32)`.

Сцена 187–192 кадра (≈8.0 с, средняя ночного прогона: 304.880 с / 38 сцен), 8 точек сетки = 7
forward'ов:

| канва | схема | запрос | латентных кадров | video | cond | audio | text | всего строк | 7 forward'ов |
|---|---|---|---|---|---|---|---|---|---|
| 448×288 | сейчас, i2v 192 к | 192 | 57 | 7 182 | 126 | 640 | 250 | **8 198** | 7.55 мин |
| 448×288 | латент m=0 | 192 | 57 | 7 182 | 252 | 640 | 124 | **8 198** | 7.55 мин |
| 448×288 | латент m=1 | 209 | 62 | 7 812 | 882 | 696 | 124 | **9 514** | 9.15 мин (**+21%**) |
| 896×512 | сейчас, i2v 192 к | 192 | 57 | 25 536 | 448 | 640 | 572 | **27 196** | 41.1 мин |
| 896×512 | латент m=0 | 192 | 57 | 25 536 | 896 | 640 | 124 | **27 196** | 41.1 мин |
| 896×512 | латент m=1 | 209 | 62 | 27 776 | 3 136 | 696 | 124 | **31 732** | 52.5 мин (**+28%**) |

**m=0 бесплатен ровно.** Один латентный кадр кондиционирования прибавляется, блок зрения той же
величины уходит — сумма не меняется, и запрашиваемая длина остаётся прежней (187 доставленных +
5 подрезанных = 192). m=1 добавляет 17 кадров к запросу и 5 латентных кадров кондиционирования.

Честная оговорка: `docs/RESULTS.md` предупреждает, что модель предсказывает **только диффузию**;
ночной прогон шёл ~10.3 мин/сцену против 7.55 мин расчётной диффузии, остальное — загрузка и
декод. Декод при m=1 растёт пропорционально кадрам (+9%). Итог по ночному прогону: m=0 — без
изменений, m=1 — примерно **+1 ч 10 мин к 6 ч 31 мин**.

Ещё две правки не в диффузии, а в её пользу: латентная сцена **не грузит видео-VAE ради энкода**
(`h3_48gb/pipeline.py:336`, 5.21 ГБ туда-обратно на каждую сцену) и **не гоняет башню зрения**.

## 2. Только видео. Что теряем и почему это приемлемо

Аудио-латент не переносим. Это не выбор из лени, а отсутствие механизма:
`build_packed_sequence` возвращает `num_condition_audio_rows=0` безусловно (packing.py:344), и
никакой раскладки для аудио-строк кондиционирования в упакованной последовательности нет.
Скелет вокруг существует — `PackedSequence.audio_indices` документирован как «reference rows
first (ref2va), then target rows» (packing.py:85), `build_row_timesteps` уже умеет пришпилить
первые `n_cond_a` аудио-строк (packing.py:369–374), `_row_timestep_plan` уже передаёт им
таймстеп 1.0 (upstream pipeline.py:135) — но **сами строки никто не строит и не кладёт**.
Это новая функциональность, а не перенос: нужна временная раскладка аудио-условия на 40-Гц сетке,
её сшивка с видео-часами `5/3` и решение по шумовой аугментации, ни на что из чего в порте нет
образца. Recon §6(c) приходит к тому же выводу.

**Что теряем конкретно:** стык звука между сценами при `audio_mode="clips"`
(`assemble.py:630, 315`) — там собственный звук клипов и есть финальный звук, и на каждой склейке
останется ровно тот же щелчок/скачок тембра, что и сейчас. При `audio_mode in ("song","mix")`
(`assemble.py:641–670`) диегетический звук либо полностью заменяется треком (`_mux_song_audio`,
:519), либо ложится под него (`_mux_mixed_audio`, :534) — в первом случае мы не теряем ничего
вообще, во втором теряем меньше, чем слышно под песней.

Целевой сценарий — клип: `kind="clip"` по умолчанию `audio_mode="song"` (`assemble.py:134–139`).
Поэтому цена аудио-половины для нас близка к нулю, а стоимость постройки — выше, чем всей
видео-половины вместе взятой. **Не строим.**

Побочный эффект, который надо назвать: перенос видео-контекста без аудио-контекста — режим, в
котором ни Motion-Context, ни Continuum по умолчанию не работают (оба тянут пару). Ссылка
`kind: "video"` без `audio_latent` у обоих структурно возможна (recon §3, «Separability: yes»), но
это не то, на чём они мерили свои 0.95 кросс-корреляции по шву.

## 3. Взаимодействие с паллиативом `fresh_start`

`fresh_start` в коде ещё нет (grep по репозиторию на 2026-08-25 не находит его нигде) — внедряется
параллельно. Постановка: BACKLOG.md, «P0 Кейфрейм-цепочка тащит персонажей МИМО их ухода» — рвать
цепочку там, где сценарий меняет состав, ценой скачка на склейке.

**Сцена с разрывом латент не получает.** Это не компромисс, а определение: латент несёт *больше*
предыдущей сцены, чем кейфрейм, значит на границе, которую мы рвём именно для того, чтобы
предыдущая сцена не протекала, он вреден вдвойне.

**Сцена без разрыва: латент ВМЕСТО кейфрейма, не вместе.** Обе схемы продуманы:

*Схема A — латент вместо картинки (рекомендуется).*
Строк: нейтрально при m=0, +21/28% при m=1 (§1.5). Промпт теряет `SCENE_I2V_INSTRUCTION`.
Из цепочки уходят `_extract_keyframe` и каталог `keyframes/`.
**Плюс, который легко проглядеть:** сейчас автокейфрейм берётся не с конца клипа, а за
`KEYFRAME_LEAD_SECONDS = 1.5` до него (`assemble.py:116–118`) — то есть на каждом стыке действие
откатывается на полторы секунды назад. Латентный хвост берётся с фактического конца, и этот
структурный откат исчезает вместе с ним. Это отдельная, независимая от «плавности» победа.

*Схема B — латент И картинка.*
Кажется бесплатной страховкой, но: первый пришпиленный латентный кадр стоит в пиксельном индексе
0, и якорь `"first"` картинки — там же. Два блока условия на одной временной координате — ровно
та конфигурация, которую фикс I3 в `_scene_generate_args` (`assemble.py:983–991`) описывает как
«H3 читает это как *две* ссылки на кейфрейм в 0.00 с» и специально предотвращает для текста.
Плюс +126/+448 строк условия и +126/+448 строк зрения (§1.5). Оправдана схема B только тогда,
когда картинка — **другая**: кадр от иллюстратора под смену состава. Но это и есть случай
`fresh_start`, где латента как раз нет.

**Рекомендация:** схема A на не-разорванных стыках, ничего на разорванных. Один флаг сцены
(`fresh_start`) управляет обоими: `True` → ни `--latent`, ни автокейфрейм; `False` → `--latent`.
Разорванная сцена по-прежнему обязана сохранить свой хвост (`--save-latent-tail`), иначе
следующая за ней сцена останется без входа.

## 4. Риски, по-честному

### 4.1 Снап длительности против длины переносимого хвоста — главный риск, и он арифметический

Сцены уже жёстко посажены на сетку `17n+5` кадров: `_snap_scene_duration` (`web.py:883–920`)
снапает **вниз** и переносит остаток в `carry`, `_grid_frames_at_or_below/above` (`web.py:869,877`)
— сама сетка, `_SNAPPED_COVERAGE_SHORTFALL_SECONDS = 1.0` (`web.py:932`) — сколько суммарно
позволено недобрать против трека, `DURATION_TOLERANCE_SECONDS = 0.5` (`assemble.py:139`) — допуск
финала.

Арифметика переноса: запрос `R` должен быть на сетке (`align_num_frames`, packing.py:125–131,
всё равно округлит вверх), доставленное `D = R − (17m+5)`. Отсюда `D = 17(n−m)` — **кратно 17, но
не вида `17k+5`**. То есть у сцепленной сцены достижимая сетка длительностей *другая*, чем у
сцены 0.

Если этого не сделать: каждая сцепленная сцена отдаёт на `17m+5` кадров меньше обещанного. При
m=1 это 0.917 с × 37 сцепленных сцен ночного прогона = **33.9 с недобора** против допуска 0.5 с.
Сборка упадёт детерминированно, а `_pad_with_freeze_frame` (`assemble.py:498`) попытается
заклеить это 34 секундами замороженного кадра. При m=0 — 0.208 с × 37 = 7.7 с, всё равно на
порядок больше допуска.

Правка: `_grid_frames_at_or_below/above` параметризуются шагом и остатком (`17k+5` для сцены 0,
`17k` для сцепленной), `_snap_scene_duration` получает признак сцепленности, `carry` работает как
и работал. Чистая арифметика, полностью покрывается модульными тестами без GPU — но **её надо
сделать до первого прогона цепочки**, иначе первый же полный клип упадёт на сборке.

### 4.2 Чекпоинт / резюм сцены с латентным входом — identity digest

`request_identity` (`checkpoint.py:150–179`) кладёт в идентичность прогона дайджест каждой
картинки (:173–174, через `_image_digest`, :106–132). **Латентный вход обязан попасть туда же
по содержимому.** `_image_digest` для `Path` уже хеширует байты файла (:119–121), так что
механизм есть — надо только провести путь хвоста через него отдельным полем `latent`.

Что произойдёт без этого: сцену N-1 перегенерировали («пересчитать сцену»), файл хвоста
перезаписался, а прерванная сцена N возобновляется по старому дайджесту и **дописывает клип,
первые шаги которого были расшумлены под другой контекст**. `_check_seam`
(`checkpoint.py:554–580`) это не поймает: он сравнивает `video_cond` из чекпоинта с тем, что
прогон построил заново, а прогон построит ровно то, что лежит в файле сейчас — совпадение будет
идеальным и ложным.

Дальше по мелочи, но обязательно:
* **`FORMAT_VERSION` (`checkpoint.py:59`) бампнуть.** Смысл строк условия меняется.
* Число строк условия входит в форму `condition_noise` (upstream :276), а он тянется **первым** из
  генератора запроса (upstream :272–280) — значит любое изменение L сдвигает весь дальнейший поток
  шума, и латенты видео/аудио тоже. Идентичность это ловит через `keyframe_anchors` (он в
  `arguments`), так что резюм защищён. Но **A/B «до и после» на одном сиде невозможен в принципе**
  — это вопрос дизайна ворот (§5), а не баг.
* `_release_vae_after` (`h3_48gb/pipeline.py:362–375`) в латентной ветке не вызывается — VAE не
  грузился. Убедиться, что `mx.eval(condition_rows)` всё равно происходит до входа в цикл, иначе
  ленивый граф над `mx.load` доживёт до первого forward.

### 4.3 `framecheck` на первых кадрах

`_validate_decoded_frames` (`h3_48gb/pipeline.py:213–239`) прогоняет `find_corrupt_frames`
(`framecheck.py:236`) по **всем** декодированным кадрам, включая те `17m+5`, которые будут
срезаны. Новых ложных отказов это само по себе не создаёт, но два обстоятельства стоит назвать:

* **На 448×288 живёт только детектор нулевой заливки.** `tile_seam_score` возвращает чистую 1.0,
  если точек замера меньше `MIN_SEAM_POINTS = 11` (`framecheck.py:157`), а 448×288 порог не
  проходит никогда — это зафиксировано в докстринге модуля (`framecheck.py:26–36`). Значит
  латентный хвост, взятый с ночного 448×288-прогона, прошёл проверку только наполовину.
* **Из цепочки уходит проверка кейфрейма.** `_extract_keyframe` (`assemble.py:1023–1063`) сейчас
  шагает назад до `_KEYFRAME_SEAM_MAX_LOOKBACK_FRAMES = 24` кадров в поисках некорраптного кадра
  и **отказывается** сцеплять цепочку на битом кейфрейме. Латентный хвост берётся вслепую: он
  никогда не декодируется отдельно. Компенсация есть — клип-источник уже прошёл
  `_validate_decoded_frames` целиком перед записью mp4 (`h3_48gb/pipeline.py:442`), то есть его
  хвост валидирован. Но валидирован **тем же** детектором, который на 448×288 наполовину слеп.
  Это не регресс, но и не та же гарантия.
* Ещё один аргумент за `KEYFRAME_LEAD_SECONDS = 1.5`: он существует в том числе потому, что
  «предпоследняя секунда» надёжнее самого конца. Латентный хвост — это как раз самый конец.

### 4.4 Память

Сами строки условия ничтожны: 1.18 МБ float32 при 896×512/m=1 (§1.3). Значимо только удлинение
последовательности: +4 536 строк при 896×512/m=1. По оценке очереди
`peak_gb = 9.3 * rows / 37657 + weights` (`web.py:1957`) это
**+1.12 ГБ** к пику диффузии. Против 28.2 ГБ пика текстового энкодера (который к моменту
диффузии уже выгружен, `h3_48gb/pipeline.py:188–210`) и ~32 ГБ пика диффузии на 10 с нативно —
реально, но не обрыв. При m=0 роста нет вовсе.

В минус к пику: латентная сцена не грузит видео-VAE на энкод (5.21 ГБ, `h3_48gb/pipeline.py:366`)
и не поднимает башню зрения (1.1 ГБ, `h3_48gb/pipeline.py:278–281`).

### 4.5 Идентичность персонажей — не лечит, и, вероятно, делает хуже

Recon §7 не оставляет места для толкований: ни один из двух проектов не заявляет удержания
личности, README Continuum прямо перекладывает это на текст промпта каждого куска, а «identity» в
их коде — SHA-256 для кэша перегенераций. Покупается **плавность движения и композиции на стыке**,
и только она.

Более того, для нашей конкретной P0 из ночного прогона («Альдред в кадре до финала, младенец на
руках до 256-й, меч не появился») приём работает **в противоположную сторону**: провал вызван
тем, что композиция предыдущей сцены побеждает текст, а латентный хвост переносит предыдущую
сцену *полнее*, чем кейфрейм. Ожидание — не «станет лучше», а «на не-разорванных стыках станет
глаже, на границах смены состава станет хуже, поэтому там мы его и не даём» (§3).

Единственная оговорка в пользу приёма, и она честно спекулятивная (recon §7, последний абзац): на
коротком горизонте через шов проезжает больше реальной информации, чем через один пере-сжатый
кадр, поэтому одежда/поза/освещение *в первые полсекунды* держатся, вероятно, лучше. Это про
непрерывность, а не про то, что модель начала различать персонажей. **Ни одного замера дрейфа
личности ни в одном из разобранных репозиториев нет.**

### 4.6 Мало шагов + turbo

Оба проекта предупреждают: чем агрессивнее ускорение, тем хуже непрерывность (recon §5,
BACKLOG). Мы гоняем 8 точек сетки = 7 forward'ов (`cli.py:59`) с `SCENE_TURBO_STRENGTH = 0.45`
(`assemble.py:106`). Пришпиленные строки стоят на 0.999 все семь шагов — у модели крайне мало
итераций, чтобы согласовать своё поколение с пришпиленным окном. Цифры 0.95 кросс-корреляции по
шву у Motion-Context получены не на семи шагах. **Не переносить их ожидания на нашу сетку;
мерить своё.**

### 4.7 Разрешение внутри цепочки

Латент нельзя ресайзить; оба проекта в этом случае падают, а не откатываются на пиксельный путь
(recon §5). У нас канва цепочки фиксирована (`DEFAULT_SCENE_CANVAS`, `assemble.py:91`), так что
сегодня это не проблема — но загрузчик обязан **отказывать громко** при несовпадении формы, а не
пытаться подогнать (§1.2).

### Порядок

1 → 2 → 3 — на этом месте механизм доказуем **одной парой ручных `h3 generate`** без единой
правки в проектном конвейере: сгенерировать сцену A с `--save-latent-tail`, сцену B с `--latent`,
посмотреть на стык. Это самая дешёвая точка отказа, и до неё ~12–16 ч.
Дальше 4 (иначе резюм тихо врёт), дальше 6 **обязательно до** первого прогона цепочки (иначе
сборка падает арифметически, §4.1), дальше 5, дальше 7.

Правило репозитория соблюдать буквально: **тест не написан, пока не увиден красным** (the repository rule).
Здесь особенно опасен раздел 1 — «фикстура энергична, реальный конвейер ленив»: тест на якоря,
собранный на уже материализованных массивах, увидит только форму, а не координаты. Утверждать
надо конкретные значения `position_ids[:, 0]` для пришпиленных строк, а не их количество.
И план обязан быть проверен против спеки тем, кто его не писал.

### Критерий ворот

**Метрика — отношение, а не абсолют.** На готовом `final.mp4`: для каждого стыка в момент `T`
взять покадровую разность `d_seam = mean|Y(T) − Y(T − 1/24)|` и сравнить её с медианой такой же
разности внутри соседних клипов: `seam_ratio = d_seam / median(d_inside)`. Порог **не назначать
заранее**: сначала измерить `seam_ratio` на уже существующем ночном рендере (38 сцен, готов,
GPU не нужен) — это и есть baseline. Ожидание: сегодня он большой не только из-за пере-сжатия,
но и структурно, из-за отката на `KEYFRAME_LEAD_SECONDS = 1.5` (§3). Успех — статистически
значимое падение `seam_ratio` на сцепленных стыках при неизменной медиане внутри клипов
(последнее важно: приём не должен «улучшать» метрику, размазав движение везде).

**Проверка подрезки — отдельно и строго.** Число кадров доставленного клипа обязано быть ровно
`R − (17m+5)`, а его первый кадр — **не** быть почти-дубликатом последнего кадра предыдущего
клипа. Это детерминированная проверка, ей место в тесте, а не в глазах.

**Глаза — обязательны и решают.** Тот же фрагмент из 4 сцен, три стыка, слепое A/B, один вопрос:
«видно склейку или нет». MEMORY.md фиксирует общее правило проекта — техника это порог, провал
замысла видит только человек. Метрика здесь нужна, чтобы не обманываться, а не чтобы принимать
решение вместо человека.

**Чего ворота не проверяют:** сохранность личности персонажей. Мерить её на этом приёме
бессмысленно (§4.5) — и указывать её в отчёте как «не изменилось» тоже нечестно, потому что
поток шума меняется (§4.2) и сцены получатся другими по любой причине.

## 6. Что изменило бы ответ

* **Если m=0 не сдвигает метрику шва, а m=1 сдвигает.** Тогда приём перестаёт быть бесплатным и
  становится решением про бюджет: +21% (448×288) / +28% (896×512) диффузии, ~+1 ч 10 мин к
  ночному прогону. Это первое, что надо померить, и до этого замера любая оценка «стоит ли» —
  выдумка.
* **Если пришпиленные строки должны быть чистыми, а не зашумлёнными до 0.999.** Тогда
  `build_row_timesteps` (packing.py:348) нужен третий класс строк, а `_row_timestep_plan`
  (upstream pipeline.py:125) — третий таймстеп, и раздел §1 удлиняется заметно. Recon это прямо
  оставляет нерешённым; два прогона по 10 мин закрывают вопрос.
* **Если кто-то соберётся строить аудио-кондиционирование.** Тогда §2 перестаёт быть данностью,
  `audio_mode="clips"` становится пригодным для сцепленных клипов, и приём начинает окупать
  вдвое больше. Но это отдельная стройка, дороже всей видео-половины.
* **Если цепочка перейдёт на нарисованные иллюстратором стартовые кадры каждой сцены** (то самое
  лечение P0 из BACKLOG) — доля стыков, где перенос латента вообще применим, схлопывается до
  «стыков внутри одного плана». Тогда 27–35 ч могут не окупиться, и приоритет P2 в бэклоге
  становится справедливым.
* **Если `seam_ratio` на существующем ночном рендере окажется мал.** Глаз говорит обратное, но
  никто не мерил. Замер бесплатен (файлы на диске, GPU не нужен) и должен быть сделан **до**
  первой строки кода.
* **Если апстрим H3 или порт получит первоклассное multi-reference-кондиционирование по
  произвольным моментам времени** — обобщение `keyframe_anchors` из §1.1 станет лишним, но
  остальные пять шестых работы (сохранение, идентичность, подрезка, сетка длительностей) — нет.
